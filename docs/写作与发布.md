# 写作与发布

面向博客作者本人的操作手册。项目本身是什么、怎么跑起来，见 [README](../README.md)。

---

## 写一篇新文章

```bash
npm run new "文章标题"
npm run new "文章标题" -- --category 随笔 --tags 读书,随想
```

会在 `src/content/posts/` 下生成一份 frontmatter 正确的骨架，**直接编辑那个文件写正文**即可。

可选参数：

| 参数 | 说明 |
|---|---|
| `--category <分类>` | 单个分类。留空则不设 |
| `--tags a,b,c` | 逗号分隔 |
| `--slug <自定义>` | 默认取标题 |
| `--date <YYYY-MM-DD>` | 默认今天 |
| `--archived` | 标记为归档 |

命令会自动做三件事：

1. **清洗文件名**里的 `#`、空格、全角冒号等字符 —— 这些会让构建读不到文件
2. **保留 frontmatter 的 `slug` 原样** —— 它决定文章 URL，不能随便动
3. 列出当前已有的分类，避免写错别字导致分类页多出一个孤零零的入口

> 为什么要有这个命令：`title` / `date` / `slug` 是 schema 必填项，手写漏一个，
> 构建会**直接失败**。用脚手架就不会漏。

## frontmatter 字段

```markdown
---
title: "文章标题"          # 必填
date: 2026-09-18           # 必填
slug: "my-new-post"        # 必填，决定 URL
categories: ["随笔"]        # 可选
tags: ["标签A", "标签B"]     # 可选
archived: false            # 可选
description: "摘要"         # 可选，缺省时自动截取正文前 120 字
---
```

**`archived: true`** 的文章不出现在首页、归档页和 sitemap，**但直链仍可访问**。
旧站的 27 篇 Effective C++ 条款笔记就是这样处理的（内容薄、同质化重）。

图片放 `public/` 下，用根路径引用：

```markdown
![说明](/images/foo.png)
```

代码块正常写，会自动带语言标签和复制按钮：

````markdown
```python
print("hello")
```
````

## 本地预览

```bash
npm run dev          # http://localhost:4321，改完自动刷新
```

> ⚠️ **不要用 `npm run preview` 验证中文标题的文章。**
> 那是 Astro 自带的简易静态服务器，**不解码百分号编码**，中文 URL 一律 404。
> 那不是站点坏了 —— 这个坑我踩过，排查了很久。要本地验证用 `npm run dev`。

## 发布

```bash
npm run publish:prepare -- src/content/posts/2026-10-20-foo.md public/images/foo.png
npm run publish -- "新增文章：XXX"
```

发布分两步，中间可以停下来审阅。**只列出本次要发布的文件**，未列出的改动不会被带走。

### 1. `publish:prepare`：固定文件并检查

1. 拒绝 `node_modules` / `dist` / `.astro` / `.git` 下的路径和目录参数
2. 确认每个文件确实有未提交改动
3. 本地构建 —— frontmatter 写错会在这里被拦住
4. 核对每篇文章（含归档）在 `dist` 里都有对应路由，且没有重复
5. 把文件列表、SHA256、当前 HEAD 写进 `.astro/blog-publish-plan.json`

这一步不会提交、不会推送，也不会动暂存区。

### 2. `publish`：提交、推送、等部署

1. 核对清单里的文件自 prepare 后没有变化，且暂存区是干净的
2. **只暂存清单里的文件**并提交
3. 推送 `master`
4. 等待这个 commit SHA 对应的 Actions 结束（最多 10 分钟）
5. 抽查首页和本次新增/修改的文章 URL（最多再等 3 分钟）

失败时会给出具体原因和 Actions 链接；只有失败时才需要读日志。

```bash
npm run publish -- --dry-run    # 只检查清单和哈希，不提交
```

清单文件在 `.astro/` 下（已被 gitignore），过期或手动改过文件都会在发布前被拦下。重新跑一次 `publish:prepare` 即可刷新。

需要 Node >= 22.12；本机默认 Node 20 时，把 22 放到 PATH 前面：

```bash
PATH=/opt/homebrew/opt/node@22/bin:$PATH npm run publish:prepare -- <文件...>
```

## 改简介 / 站点信息

**全部集中在 `src/site.config.ts` 一个文件里**：

| 想改什么 | 改哪一项 |
|---|---|
| 侧栏那行简介 | `bio` |
| 站点标题（左上角） | `title` |
| SEO 描述 | `description` |
| 作者名 | `author` |
| 头像 | `avatar`（图片放 `public/images/`） |
| 导航菜单 | `menu` —— **改之前先看下节** |
| 社交链接 | `social` |
| 友情链接 | `links` |
| 每页文章数 | `POSTS_PER_PAGE` |

改完 `npm run dev` 立刻能看到效果，满意了再 `npm run publish`。

## ⚠️ 改导航前必读

导航**刻意只有 4 项**：`首页 / 归档 / 标签 / 关于`。这是有意的设计决定，不是漏了：

- **`Sitemap` 不在导航里** —— 它是给爬虫的 XML 文件，人点进去是一坨原始 XML。
  已放在页脚，需要时仍可访问。**不要放回导航。**
- **`Categories` 不在导航里** —— 它与 `Tags` 内容严重重叠（分类只有 6 组、
  标签 67 个，`算法`/`java`/`C` 同时出现在两边），两个平级入口让人无从选择。
  页面**保留**（`/categories/` 仍可访问，从标签页与文章元信息进入），只是不占导航位。
- **首页没有 H1**（只有卡片列表）也是**有意为之** —— 它和内页共用同一套容器语言，
  差异读起来是设计而非遗漏。**别给它加标题。**

以上三条的理由详见 [维护笔记](维护笔记.md)。
