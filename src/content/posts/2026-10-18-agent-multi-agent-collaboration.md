“让一个 Agent 实现，再让另一个 Agent 审核”，听起来就比单个 Agent 可靠。但增加角色，并不会自动增加正确性。两个角色可能沿用同一套错误前提，也可能在交接中丢失关键条件。

《深入理解 AI Agent》第 10 章的价值，在于把注意力从角色命名转向协作机制：为什么拆、信息怎么传、谁能修改产物，以及凭什么判断完成。

## 先说清额外 Agent 带来什么

我会从四类收益评估一个拆分方案：

1. **并行探索**：几个相对独立的方向同时推进，降低任务墙钟时间。
2. **上下文隔离**：每个执行者专注局部问题，减少无关轨迹干扰。
3. **专门能力与工具**：不同角色使用适合任务的模型、工具或权限。
4. **独立验证**：审核者查看原始证据、运行结果或渲染效果，检查实现者的结论。

外部反馈尤其有价值，但“只有引入新信息，多 Agent 才可能有用”说得过于绝对。并行、不同搜索路径和上下文容量本身也可能带来收益。是否有效，需要与同等预算下合理配置的单 Agent 方案比较。

Anthropic 的[多 Agent 研究系统介绍](https://www.anthropic.com/engineering/multi-agent-research-system)强调了独立上下文中的并行探索，也明确指出紧密依赖、需要共享大量背景的任务并不适合简单拆分。这里提供的是特定研究系统的经验，不能直接当作所有任务的性能结论。

如果几个角色只是轮流复述同一段材料，没有独立证据，也没有清楚的分工，就应该先质疑这层编排的必要性。

## 上下文共享与协作拓扑是不同选择

上下文可以较多共享，也可以相互隔离。共享方便接力，减少重新解释背景的工作，但容易累积无关信息；隔离便于并行和权限收敛，却增加交接成本。

共享历史不意味着信息零损耗：内容可能被截断、压缩或忽略。独立上下文也不意味着必须丢失重要信息，可以通过任务契约、证据链接和结构化结果减少损失。

不要用固定的“窗口超过一半就拆分”作为通用阈值。任务依赖、关键资料大小、实际失败表现和成本预算，比一个未经验证的比例更重要。

协作拓扑则回答谁负责调度：

| 方式 | 更适合的情形 | 需要处理的问题 |
|---|---|---|
| 主执行者与独立审核者 | 有明确产物和验证方式 | 审核是否拿到独立证据 |
| 管理者分派多个执行者 | 可拆成边界清楚的子任务 | 重复工作、遗漏、汇总瓶颈 |
| 按条件移交角色 | 随问题类型转交专业处理 | 循环移交、责任不清、状态丢失 |

这些方式可以混合。使用什么框架，也不能单独证明系统是中心化或去中心化；要看实际控制流。

## 交接需要任务、证据和边界

给子任务一句“研究一下这个问题”，通常不够。至少应说明目标、输入、范围、可写位置、输出形式、完成条件和预算。

例如，把文档核验拆出去时，可以要求：核对指定章节中的事实性主张，返回原文位置、核验结果与不确定项；不修改正文，不把无法验证的内容当成错误。

返回结果也不应只有一段很自信的摘要。更可用的结果包含：

```text
结论：哪些主张得到支持，哪些仍不确定
证据：来源、版本、原文位置
产物：文件路径或结构化数据
限制：未覆盖的范围、失败的检查
状态：完成、部分完成或受阻
```

大产物可以传路径，减少反复搬运内容，但接收者必须确实有权限访问。必要时还应记录版本或校验值，避免读取到后来被覆盖的文件。

## 并行写入会引入新的错误

多个 Agent 同时改同一份文件，可能发生覆盖；即使改的是不同文件，也可能出现接口、命名或引用不一致。文件级没有冲突，不等于语义上没有冲突。

可以采用明确的文件归属，或使用独立分支与 worktree，最后统一合并并验证。版本校验能够发现某些覆盖，却不能自动识别跨文件设计矛盾。

隔离上下文也不是权限隔离。一个角色在提示词里被要求“只读”，但实际拥有写权限，仍然不能等同于强制只读。需要的约束应由工具和运行环境落实。

## 审核要避免重复前序错误

审核者如果只看实现者总结，容易继承其遗漏。对关键判断，应能够回到需求、原始资料与实际产物。

代码审核可以结合测试和变更内容，界面审核可以看真实渲染，事实审核可以核对一手来源。但这些证据也有边界：测试会漏测，截图可能过期，资料可能不适用于当前版本。

独立审核的意义是增加发现错误的机会，而不是再盖一个必然正确的章。关键事实仍然需要明确证据与适用条件。

## 预算和终止也是协作机制

多 Agent 增加的不只是模型调用，还包括分工说明、重复读取、状态查询、结果汇总与失败恢复。并行可能更快，也可能因协调而更慢；总 token 也不一定与执行时间同步下降。

任务应有总预算、并发上限、重试与移交上限。主任务取消后，还需要处理子任务、工具进程和临时资源，不能只停止主 Agent 的输出。

最终评估应同时看结果质量、延迟、总成本、交接错误与恢复难度。如果一个合理配置的单 Agent 已经稳定完成任务，就需要具体证据说明增加角色解决了什么瓶颈。

我会把多 Agent 作为一种有成本的系统设计选择：先找到可以拆分的边界与可验证的收益，再决定是否引入协作。
