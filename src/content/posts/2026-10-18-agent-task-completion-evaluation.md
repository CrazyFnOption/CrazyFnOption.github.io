“代码改好了”“报告发出去了”“任务已经完成”，都只是 Agent 的声明。评估要回答的是：目标是否达成，有什么证据，以及是否通过允许的方式达成。

这是整理《深入理解 AI Agent》评估章节时最有用的一条主线。一个能流畅解释过程的系统，仍然可能漏做步骤，或者把工具调用成功误当成业务成功。

## 先写清完成条件

以“生成并发布一份报告”为例，完成条件可以拆成：

| 层次 | 验收问题 | 可用证据 |
|---|---|---|
| 产物 | 文件存在、能打开、内容完整吗？ | 实际文件与渲染结果 |
| 内容 | 数字与来源一致，关键要求都覆盖了吗？ | 原始数据、逐项检查 |
| 发布 | 发布系统是否成功，目标地址能否访问？ | 部署状态与线上页面 |
| 过程 | 是否越权发布或暴露私人资料？ | 授权范围、操作记录与产物审查 |

“调用过发布命令”只能证明尝试过动作。“命令返回成功”可能只表示提交进入队列，不能替代最终状态检查。

完成条件应允许多种有效路径。任务要求的是正确报告，就不能因为 Agent 没按某条参考轨迹操作而判失败；但如果明确要求保留原始数据，这项过程约束就需要单独验收。

## 结果、过程和表达要分开看

结果验证检查事情是否办成。能查询真实状态时，优先读取系统中的产物、数据库记录或部署结果，避免仅评判最后一段回复。

过程验证检查动作是否在授权范围内、是否满足必要约束。通过删除测试获得“全部通过”，和在保留测试的条件下修复问题，不能算同一种成功。

表达质量再用来判断说明是否清楚、依据是否充分、是否承认不确定性。语言评分不能抵消关键结果缺失，也不应让严重越权被其他高分平均掉。

验证器本身也可能出错。测试没有覆盖需求、查询的是旧环境、截图来自旧版本，都能产生虚假的确定感。应检查证据与当前任务、版本和时间是否对应。

## 对“做不了”也需要验证

任务没完成至少有几种不同情况：

- 宣称完成，但漏做了必要工作。
- 操作已执行，但结果不满足要求。
- 还有可行路径，却过早认定无法完成。

第三种很容易被忽略。遇到工具异常，应区分接口暂时失败、权限确实不足、前提缺失与任务本身不可行。“第一次尝试失败”通常不足以证明任务无法完成。

这也不意味着无限重试。运行需要明确预算、重试上限和终止条件；达到边界后，说明已验证的阻碍、保留的产物与下一步所需条件。

## 一次成功与稳定成功是两回事

[Anthropic 的 Agent 评估文章](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)区分了两个容易混淆的指标：`pass@k` 关注多次尝试中至少成功一次，`pass^k` 关注多次尝试全部成功。

为了看清差别，假设同一任务每次成功率固定为 `p`，各次尝试相互独立，则：

```text
至少一次成功：1 - (1 - p)^k
全部成功：p^k
```

当 `p = 0.6`、`k = 5` 时，前者约为 `98.98%`，后者约为 `7.78%`。这只是满足上述假设的概率示例，不是某个 Agent 的实测成绩。

真实任务难度不同，尝试也可能相关，因此不能把整套任务的平均成功率直接代入，就当作严格估计。报告结果时应保留任务数、每题尝试次数、运行设置和实际分布。

还有一个产品层面的条件：重试五次虽然更容易包含一次成功，系统是否能可靠识别那次成功？如果无法识别，用户仍不能直接获得这个理论收益。

## 评估的是完整系统

模型、提示词、检索、工具、权限、环境与终止策略共同影响结果。换模型后分数没涨，可能是工具信息不足，也可能是评估集不敏感、预算限制或其他因素；不能据此直接断言模型没有作用。

更有解释力的做法是：固定其他条件改变一个因素，用相同任务比较，并检查失败轨迹是否支持假设。例如，怀疑页面元素缺失，就检查实际观察输入，再比较不同观察方式，而不是只把提示词改得更长。

同时记录成功率、延迟与成本。便宜但频繁失败的方案，算上重试后未必更经济；成功率稍高的方案，也未必值得显著增加每次任务的时间。

## 从少量真实失败建立评估集

不需要先构建一个庞大的排行榜。可以从手工检查过的典型任务、边界条件和真实失败开始，保存初始状态、任务要求、完成定义与证据。

用于改提示词或调工具的任务，与最终验收的留出任务应分开。否则很容易把记住某几道题误当成能力提升。

开放式写作可以引入模型评分，但评分标准要具体，并与人工判断校准。尽量避免“表现出深刻理解”之类难执行的标准；更可操作的是检查关键事实是否正确、反例是否覆盖、结论是否有证据支持。

可靠评估最终应能说明：哪项完成条件通过了，哪项没有通过，证据在哪里，下一次修改准备解决什么。只有总分、没有可定位证据，很难帮助系统改进。
