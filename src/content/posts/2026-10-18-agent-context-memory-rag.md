读《深入理解 AI Agent》的上下文与记忆章节时，最值得先厘清的是：上下文、长期记忆和 RAG 并不是三个互相替代的方案。它们分别回答“这次模型能看到什么”“哪些信息值得跨会话保存”“如何把外部证据找回来”。

如果把三者都叫作“给模型增加记忆”，很容易得到一个看似完整、实际不可靠的设计：所有聊天进入向量库，下一次检索几段，就认为 Agent 已经理解了用户。

## 先看一次任务的信息流

假设一个资料助手接到任务：“按照上次确定的口径，整理这份报告。”它可能需要四类信息：

| 信息 | 应如何管理 |
|---|---|
| 本次报告、当前目标与限制 | 进入本轮上下文 |
| 用户长期采用的写作偏好 | 从长期记忆中读取 |
| 上次讨论口径的原始记录 | 按需检索，并保留证据来源 |
| 本次报告是否已保存、是否已发布 | 读取文件或业务系统的真实状态 |

最后一项尤其容易混淆。记忆里写着“报告已发布”，不等于发布系统里确实有这份报告。**描述状态的文字与状态本身，需要分开管理。**

## 上下文是本次推理可见的信息

对一次模型调用来说，上下文可以包含系统规则、用户请求、部分对话、工具定义、工具结果，以及从外部存储取回的资料。

长期记忆即使保存得很好，如果没有被读取并提供给这次调用，也不应指望模型能够使用它。反过来，一段临时工具输出进入了上下文，也不意味着它值得永久保存。

上下文管理因此有两个问题：装不装得下，以及装进去的内容是否有用。窗口足够大，也可能混入过期计划、重复输出和互相矛盾的结论。压缩可以减少长度，但会丢失细节；遇到关键数字、约束或争议，仍然需要回读原始证据。

Anthropic 的[上下文工程文章](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)也把压缩与持久化笔记作为不同手段：笔记存于窗口之外，在需要时重新读入。这个区分比单纯追求更长的窗口更有用。

## 长期记忆需要选择、更新和撤销

长期记忆的价值在于未来能继续使用，不在于保存的条数。它可以记录稳定偏好、项目约定、重要决策与历史事件；存储介质可以是文件、数据库或其他系统，不必一开始就引入向量数据库。

一条可维护的记忆，至少需要回答：它描述谁、来自哪里、适用于什么条件、是否仍然有效。例如，下面是一个示意结构，并非某个框架的接口：

```json
{
  "subject": "用户的技术文章",
  "claim": "先给结论，再解释原因",
  "source": "一次明确的用户确认",
  "scope": "技术写作",
  "status": "active"
}
```

“这一次请简短回答”未必应该升级成永久偏好；“以后技术文章都按这个结构写”则更有理由沉淀。系统推断与用户明确确认也不能混为一谈。

发生冲突时，不能简单按检索相似度选择一句，也不能无条件让时间最新的文字覆盖一切。先比较对象和作用域：针对某篇文章的例外，不一定推翻全局约定。确需替换时，应能追踪旧版本、来源和变更原因。

## RAG 是取回证据再生成的流程

RAG 的基本链路是：

```text
问题 → 检索相关资料 → 组织证据进入上下文 → 生成回答
```

它既能用于公共知识库，也能用于私人历史记录。用户记忆描述的是保存什么、如何维护；RAG 描述的是如何检索并利用资料。二者可以组合。

向量检索也只是检索的一种方式。精确术语、订单编号或错误码可能更适合关键词与结构化查询；语义表达差异较大的问题可以使用向量检索，必要时再做混合召回与重排序。

检索到相关片段，不代表已经拿到足够证据。分块可能切掉标题、日期或适用条件。“该设置默认开启”如果没有产品版本和上文，几乎无法安全使用。来源路径、章节、时间、版本与必要的相邻段落，都是证据的一部分。

## 少量概览与按需细节可以配合

一种值得尝试的组织方式是：让少量当前目标、稳定约定与关键限制保持可见；大量历史细节留在外部，需要时再取回。

例如，常驻摘要只保留“这份报告沿用已确认的术语表”，具体术语与确认记录按需读取。这样既能提醒 Agent 存在约定，又避免每轮都搬入完整历史。

这不是保证正确的固定架构。摘要可能陈旧，检索可能遗漏，读到了资料也可能理解错误。应分别检查：

1. 应保存的信息是否正确写入，临时信息是否被误存。
2. 当前任务需要的资料是否被取回，过期版本是否被误召回。
3. 回答与行动是否遵守证据中的条件，不能确定时是否说明缺口。

## 权限要先于资料进入模型

检索需要按调用者权限限定可见资料。把所有文档先交给模型，再提醒它“不要泄露”，无法代替访问控制。

外部文档中的指令性文字也不应该因为被检索出来就获得系统指令的地位。它是待分析的材料，需要保留来源和信任边界。

回到最初的问题：当 Agent “忘记了”某件事，可以沿着写入、持久化、检索、上下文组装和实际使用逐段排查。先定位断在哪一段，再决定增加存储、修改检索还是调整上下文，通常比直接堆更多历史有效。
